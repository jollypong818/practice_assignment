# 실습 04 · 검색 Hit를 Document로 변환하기 · 학습노트

**기본필수 / 강사용 코드 해설**

## 이번 단계가 필요한 이유

Document로 바꾸어도 기존 검색 조건은 그대로 필요합니다. 이번 변환은 여섯 Metadata 필드만 옮기고, 데이터에 없는 값을 추정하지 않습니다. 기본 실행은 예시를 실제 Document 객체에 담은 결과입니다. --live-db를 선택했을 때만 E5와 PostgreSQL을 사용합니다.

## 코드를 읽는 순서

### 1. to_document

본문을 page_content로, 제공된 여섯 Key를 metadata로 옮깁니다.

설명할 점: Document(page_content=..., metadata=...)를 사용합니다. 입력이 실제로 어떤 값인지 먼저 출력해 보고, 함수의 반환값이 다음 단계에서 어디에 쓰이는지 연결해서 읽습니다.

### 2. hits_to_documents

입력 순서대로 to_document를 호출해 목록을 반환합니다.

설명할 점: 빈 목록도 특별한 가짜 문서 없이 그대로 빈 결과가 됩니다. 입력이 실제로 어떤 값인지 먼저 출력해 보고, 함수의 반환값이 다음 단계에서 어디에 쓰이는지 연결해서 읽습니다.

## 결과를 해석하는 순서

1. outputs JSON의 execution과 입력 출처를 먼저 읽습니다.
2. 원문 본문·ID·위치가 출력의 어느 필드에 남았는지 찾습니다.
3. expected의 조건과 대조하고, 다르면 처음 어긋난 함수의 입력·출력부터 확인합니다.
4. reports/review.md에 “어떤 값이 근거인가?”를 자신의 말로 기록합니다.

## 확인 질문

1. Document 생성 성공이 실제 검색 성공을 뜻하나요?
2. citation_id를 항상 201로 넣으면 어떤 문제가 생기나요?
3. 빈 Hit 목록과 source_locator 누락은 왜 다르게 다루나요?

## 강사 설명 예시

**Document 생성 성공이 실제 검색 성공을 뜻하나요?**

아닙니다. 기본 실행은 준비된 Hit를 변환한 결과입니다. 실제 검색 여부는 input_source와 execution으로 구분합니다.

**citation_id를 항상 201로 넣으면 어떤 문제가 생기나요?**

실제 DB에서 나온 다른 ID가 바뀌어 답변과 원문 연결이 깨집니다.

**빈 Hit 목록과 source_locator 누락은 왜 다르게 다루나요?**

전자는 후보가 없는 정상 결과이고 후자는 출처 계약이 깨진 입력 오류입니다.
