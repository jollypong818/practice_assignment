# 실습 08 · 해설 학습 노트

## 서비스 함수와 API의 역할

`make_rag_service`는 Retriever를 실행하고 Context를 만든 뒤 Generation과 Validation을 연결합니다. `create_app`은 JSON 요청을 `RagRequest`로 검사하고 서비스 예외를 HTTP 상태로 표현합니다. 따라서 HTTP 200이라는 사실만으로 답변이 문서에 의해 지지된다고 결론 내릴 수 없습니다.

## 왜 두 k를 나누나요?

candidate_k는 DB 검색 후보 상한입니다. context_k는 검색 후보 중 모델에게 전달할 문서 수 상한입니다. 같은 후보를 얻어도 중복 청크, 전체 블록 길이 예산 때문에 실제 포함 수는 더 작을 수 있습니다. context_k=2라고 항상 두 문서가 들어가는 것은 아닙니다. 문자 길이 예산은 Token 개수가 아닙니다.

## 실제 포함 문서가 출처 허용 범위입니다

검색 후보 IDs → Context 포함 IDs → 검증된 답변의 source_ids를 순서대로 대조합니다. 서버는 포함 문서로 `by_id`를 만들고, 검증된 ID에 해당하는 원문 위치를 `sources`에 넣습니다. LLM이 파일명이나 URL을 직접 만들어 응답하도록 두지 않습니다.

## 근거 부족과 실행 실패

빈 Context이면 생성 호출을 생략하고 정보 부족을 반환합니다. 반면 모델 Timeout은 시스템이 답변 생성에 실패한 것이므로 502 `generation_error`입니다. 검색 실패를 빈 목록으로 삼거나 모델 실패를 자연스러운 근거 부족 문장으로 바꾸면 장애를 놓칠 수 있습니다.

## Fixture가 검증하는 범위

`--offline`에서도 실제 LangChain Runnable과 FastAPI 요청 검사는 실행됩니다. 그러나 검색은 의미 기반 E5 검색이 아니라 고정 문서 순서·category·k를 따르는 Fixture이고, 생성 결과도 정해진 교육용 값입니다. 따라서 이 결과로 실제 검색 품질이나 실제 LLM 정확도를 주장하지 않습니다. source_mode와 execution을 먼저 읽으세요.

## TestClient와 실제 HTTP 서버

TestClient는 같은 FastAPI 앱을 Python 프로세스 안에서 호출합니다. TCP 포트나 브라우저가 없어도 요청 검사·경로·응답을 확인할 수 있습니다. `--serve`는 사용자의 PC에서 Uvicorn 서버를 실행해 별도의 클라이언트 요청을 받습니다. smoke 관찰용 trace는 순차 실행 전용이므로 서버에는 사용하지 않습니다.

## 실제 실행에서 바뀌는 값

교육용 Fixture ID 201·202·203과 실제 DB의 생성 ID는 다를 수 있습니다. 실제 반환 ID를 조회·보존하고 숫자를 예제에 맞게 덮어쓰지 않습니다. 실제 모델의 답변 표현도 달라지므로 상태·출처·원문 조건을 기준으로 확인합니다.

## 응용·심화의 k 비교

`comparison_request`는 원본을 복사하고 context_k만 1로 바꿉니다. `--compare-k`는 같은 정상 질문에 요청 한 번을 추가하므로 모델 invoke 상한이 3회가 됩니다. 후보 목록이 같아도 포함 문서가 달라질 수 있다는 점을 먼저 관찰합니다. 작은 예제의 한 번의 답변 차이를 일반적인 성능 우열로 해석하지 않습니다.

## 강사 진행 메모

수강생이 wire_app에서 `service(...)`를 즉시 실행하지 않고 서비스 함수 자체를 create_app에 넘겼는지 확인합니다. 입력 오류 사례는 DB를 끊어서 만들지 말고 candidate_k=0을 사용합니다. 502는 고정 Timeout을 주입하여 설명하고 실제 장애를 유발하지 않습니다. 실제 DB 또는 모델을 검증할 수 없는 PC는 실행 범위를 분명히 기록하도록 지도합니다.
