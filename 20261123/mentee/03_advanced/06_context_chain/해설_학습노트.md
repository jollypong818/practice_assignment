# 실습 06 · 해설과 학습 노트

**03_advanced · 수강생용**

## Context와 출처를 함께 보관하는 이유

검색 후보는 길이·개수·중복 조건 때문에 일부만 Context에 들어갈 수 있습니다. 따라서 원래 후보 전체에서 ID를 모으면 모델에 주지 않은 문서를 출처로 허용하게 됩니다. 최종 `included_docs`와 Context를 같은 선택 과정에서 얻어야 합니다.

## Runnable 연결 읽기

`prompt | structured_model`에서 `|`는 문자열을 이어 붙이는 기호가 아닙니다. Prompt 실행 결과인 ChatPromptValue를 Structured Model의 입력으로 전달하는 순서를 만듭니다. `generation.invoke(inputs)`를 실행할 때 이 순서가 동작합니다.

## bundle 읽기

- `raw`: 실제 AIMessage와 응답 상태를 확인할 원본입니다.
- `parsed`: WireAnswer로 해석된 객체입니다. 파싱에 실패하면 None일 수 있습니다.
- `parsing_error`: 해석 실패의 원인입니다. None은 이 항목에 오류가 없다는 뜻이지 모든 업무 규칙을 통과했다는 뜻이 아닙니다.

이 실습에서는 구조화된 반환값과 출처 보관 위치를 이해합니다. 다음 실습에서 타입·상태 조합·허용 ID를 검사하고, 그 후에도 원문이 답변 주장을 지지하는지 사람이 확인합니다.

## 문자 예산의 한계

`len()`으로 셀 때 ID와 위치, 줄바꿈도 Context에 들어간 문자입니다. 문자 상한을 넘는 블록은 통째로 제외합니다. 문장을 중간에서 잘라 숫자와 예외 조건을 잃지 않도록 하는 작은 예제입니다. 실무의 모델 입력 제한에는 Token 예산을 별도로 확인해야 합니다.

## 스스로 확인할 질문

1. 지금 확인한 값은 Prompt 입력, 완성된 메시지, 모델 응답 중 어디에 있는가?
2. API 요청이 시작되는 줄은 어디이며, 어떤 오류는 그보다 먼저 발생하는가?
3. 이 결과는 실제 모델 응답인가, 고정 예시인가? 기록에서 어떻게 구분하는가?
4. 타입·Key가 맞더라도 원문과 다를 수 있는 주장은 무엇인가?
