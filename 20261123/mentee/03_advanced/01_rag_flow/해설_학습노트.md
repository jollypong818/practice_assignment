# 실습 01 · RAG 단계와 근거 대조 · 학습노트

**심화 / 수강생용 개념 설명**

## 이번 단계가 필요한 이유

이 실습은 사람이 강의 원문을 읽고 RAG 단계와 기대 판단을 기록합니다. 코드가 JSON을 저장해도 Retriever·Chat Model을 실제 실행한 것은 아닙니다. 출석 조건문은 가상 문서의 경계를 비교하는 수단이며 실제 기관의 정책 판정기로 사용하지 않습니다.

## 코드를 읽는 순서

### 1. stage_order

다섯 단계의 처리 순서를 반환합니다.

생각할 점: 검색과 생성 사이에 Context 선택과 Prompt 작성이 필요합니다. 입력이 실제로 어떤 값인지 먼저 출력해 보고, 함수의 반환값이 다음 단계에서 어디에 쓰이는지 연결해서 읽습니다.

### 2. evidence_fields

입력 Hit의 출처와 본문 필드를 보존합니다.

생각할 점: 숫자나 예외 문장을 새로 만들지 않습니다. 입력이 실제로 어떤 값인지 먼저 출력해 보고, 함수의 반환값이 다음 단계에서 어디에 쓰이는지 연결해서 읽습니다.

### 3. attendance_judgment

15분 경계와 사전 승인 예외를 원문대로 구분합니다.

생각할 점: 사전 승인이라면 운영실 확인, 그렇지 않은 1~15분은 지각, 15분 초과는 결석입니다. 0분은 비교 대상 밖으로 표시합니다. 입력이 실제로 어떤 값인지 먼저 출력해 보고, 함수의 반환값이 다음 단계에서 어디에 쓰이는지 연결해서 읽습니다.

### 4. comparison

15분·20분·사전 승인 20분 세 행에 판단과 동일 근거를 묶습니다.

생각할 점: 앞의 두 함수를 호출하여 각 행을 작성하세요. 입력이 실제로 어떤 값인지 먼저 출력해 보고, 함수의 반환값이 다음 단계에서 어디에 쓰이는지 연결해서 읽습니다.

## 결과를 해석하는 순서

1. outputs JSON의 execution과 입력 출처를 먼저 읽습니다.
2. 원문 본문·ID·위치가 출력의 어느 필드에 남았는지 찾습니다.
3. expected의 조건과 대조하고, 다르면 처음 어긋난 함수의 입력·출력부터 확인합니다.
4. reports/review.md에 “어떤 값이 근거인가?”를 자신의 말로 기록합니다.

## 확인 질문

1. 같은 검색 결과로도 두 질문의 답이 다른 이유는 무엇인가요?
2. 사전 승인이 있으면 무조건 출석인가요?
3. 조건문 결과를 RAG 실행 결과라고 부르면 왜 안 되나요?
