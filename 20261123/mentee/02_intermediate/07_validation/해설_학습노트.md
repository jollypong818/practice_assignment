# 실습 07 · 해설 학습 노트

## 왜 Schema 검사 뒤에도 출처를 확인하나요?

`source_ids`가 정수 목록이라는 조건은 “이 번호가 지금 모델에 제공된 문서에 존재한다”는 뜻이 아닙니다. 따라서 `KnowledgeAnswer`의 자료형 검사 뒤에 `set(source_ids).issubset(provided_ids)`가 필요합니다. 그 `provided_ids`는 검색 후보 전체가 아니라 **실제 Context에 들어간 문서**에서 얻습니다.

## 두 Schema의 역할

`WireAnswer`는 provider가 보내는 네 필드의 기본 구조입니다. 엄격한 자료형을 사용하므로 문자열 `"201"`을 정수 201로 자동 보정하지 않습니다. `KnowledgeAnswer`는 서버가 허용하는 길이·양수 ID 같은 추가 제약을 둡니다. 그 뒤 `validate_answer`가 중복·허용 범위와 상태 조합을 확인합니다.

- 문자열 ID: `fixture_bundle`이 WireAnswer로 해석하지 못하므로 `parsing_error`가 생깁니다. `receive_bundle`은 `output_parsing_error`로 거절합니다.
- 정수 중복 ID: 자료형은 맞아서 파싱되지만 업무 규칙에서 실패하므로 `answer_validation_error`가 됩니다.
- 미제공 ID: 양수 정수라도 Context에 없으면 업무 규칙에서 실패합니다.

## 수신 상태와 업무 상태

먼저 `raw`가 AIMessage인지, 거절 블록인지, `response_metadata.status`가 `completed`인지 확인합니다. 이 강의는 Responses API의 반환 계약을 사용합니다. `incomplete`인 메시지의 `parsed`가 우연히 존재하더라도 승인하지 않습니다.

그 다음 `status="insufficient_context"`는 정상적인 업무 응답입니다. answer는 정해진 안내문이고 source_ids는 빈 목록이며, 부족한 정보를 설명해야 합니다. API 실패를 이 상태로 바꿔 숨기지 않습니다.

## Citation이 맞아도 Grounding은 틀릴 수 있습니다

출석 v2 원문은 “15분까지 지각, 15분 초과 결석, 사전 승인 예외”입니다. 올바른 ID 201과 함께 “20분까지 지각”이라고 쓰면 ID 검사는 통과할 수 있습니다. 문장 의미를 원문과 대조해야 이 오류를 찾습니다. 자동 검사 결과와 사람의 근거 대조 결과는 서로 다른 항목으로 기록하세요.
